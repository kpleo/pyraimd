# Pyramid 0.4.0 第二轮独立审阅

审阅日期：2026-09-09。代码基线：`9c7dc4baba3c88544b85e254547b17b84a49196c`，本地标签 `v0.4.0`，分支 `dev/0.4.0`。

## 总体判断

这轮开发有明显、可核实的进步。上一轮的很多反例已经转成了有效回归，周期材料训练结构、内部能量—力检查、正常恢复与完整步导出等关键路径得到修正，真实 Al adaptive 和 MACE 持久化集成也补上了记录。不能继续沿用“只有正常原型路径可用”的上一轮评价。

不过，当前 0.4.0 仍有会影响导出数据、恢复历史和接口成本记录的具体问题，不宜将版本号升级或测试全通过直接等同于全部可靠性门槛通过。建议保留这轮成果，集中完成一个 **0.4.1 正确性补丁**，再扩大外部使用。该补丁以已定位问题及其最小回归为范围，不加入 NVT/NPT、新调度算法或新的大型材料案例。

其中最高优先级是：恢复入口仍会从孤立旧行取力并改变完整步动量，以及数组持久化把不同形状/类型但字节相同的状态混为一谈。这两项已经实际复现，超出了显示或文案问题，应在宣称恢复和在线更新可靠前修正。

本报告替代上一轮报告对“当前版本是否修好”的判断；上一轮报告继续作为问题起源和基线证据。严重性 P1/P2 与原计划的工作包优先级 P0/P1 是不同概念。

### 材料结果补充有价值，记录校正正确

独立从已有数据库和事件记录得到：

- Al 优化终态：全原子/固定层原始 fmax 为 **0.0545895092 eV/Å**，自由原子为 **0.0481556445 eV/Å**，低于 0.05。开发者把原解释改为“固定层反作用力造成报表口径差异”是正确的，无需重跑优化。
- 历史 WP08 事件中有 **57 条逻辑参考任务：56 success、1 failed**；结合报告单列的先导 SCF，为逻辑 58、物理启动 57 的历史重建。失败源于建目录阶段，不能计为已经运行一次 SCF。先导日志和历史未逐 attempt 记录的边界保留原报告说明，不冒充本轮现场观测。
- 新 Al adaptive：**6 个完成步、7 次评估、4 次 ML 驱动、4 次检查、19 次真实 reference attempt，均成功**。当前账本与事件相符。
- Al committee：**2 个完成步、3 次评估、1 次 model_update、11 次 reference attempt**。开发者的第二进程记录显示权重/能量平移恢复一致，边界力最大差 **1.39e-17 eV/Å**。这是实际补上了“真实模型落盘后能否加载”的缺口；它本身没有证明恢复后所有后续训练随机过程逐位一致。
- 已存 FD 结果的残差重算为 **4.77e-6、3.58e-5 eV/Å**，均低于事前写入脚本的 **5e-4**。本轮重算了导数与力之间的残差，没有重算五次电子结构，也没有从未归档的 ±h 输出重新提取总能量。

能量契约从“名称必须相同”改为“各自的标量势与力一致”，符合上一轮推导，值得保留。它让框架支持一般满足条件的参考/替代组合；材料验证提供具体例证，不需要把方法定义成只适用于这一块 Al 表面。

软件根据后端的 **capability 声明**判断兼容，当前并没有读取/绑定每组参数的 FD 证书。因此 README 中“未经验证的组合都会被拒绝”应改成准确区分“声明不满足契约会被拒绝”和“Al 配方另有数值验证”。无需为修正文案引入所有材料/展宽参数的白名单或逐组合验证工程。两条差分方向也不构成全局保守性的证明。

## 主审确认的残留与回归

### A1 [P1] 初始帧被错误多加半步动量

位置：`src/pyraimd2/store/store.py:134–143`。

`complete_step_frame` 对所有 `energetic_force_error` 行加 `0.5*dt*F`，但初始 evaluation 本来保存的就是完整初始动量，不是半步状态。当前初始行也带 timestep，于是被误处理。

实测：原始及数据库初始动量均为 `[0.1008,0,0]`，导出却为 `[0.09962127662538431,0,0]`，最大误差 **0.0011787233746156922**（ASE 动量单位）。帧同时被标记 `initial_evaluation` 和 `complete_step_reconstructed`。

影响：初始温度/动能和用导出帧建立的初态会被改变。这一反例证明的是导出重建错误，并未证明实际积分器把初始动量改错。

修正：按明确的 evaluation phase/初始 ID 判断，仅对真正的 MD 中间力评估补第二半步；初始帧保持原始动量。回归同时比较初始帧和至少一个后续完整步，不只检查后续行。

### A2 [P2] 优化轨迹被 MD 完成步规则全部过滤

位置：`src/pyraimd2/workflows/export.py:219–220`、`:171`。

`export_run` 无条件传入 `completed_step_ids`，而 relax 的优化迭代没有 MD 的 `STEP_COMPLETED`。空集合过滤掉所有非负 step 的优化行。

实测：一个成功的 reference harmonic relax 存有 **10 行**，执行标准 `export_run` 却报 **“no committed evaluations to export”**。同组 singlepoint 对照正常导出 1 帧，因为其 step=-1；不能把单点也列为已复现失败。

修正：根据任务类型使用 MD 完整步、优化迭代或单点评估的正确提交语义。验收至少包含三种 task 的 CLI/export；优化终态重复行应按明确的评估身份处理。对于无事件的历史运行，文档承诺的回退语义也需一致，不能将“没有日志”误作“确定没有完成帧”。

### A3 [P1] 恢复的权威行选择没有接入导出

位置：`src/pyraimd2/workflows/export.py:161–177`。

核心恢复已经通过 `committed_row` 绑定 row_id，但导出仍遍历数据库所有行，仅按 step 是否完成过滤。DB 写入后、事件提交前中断，恢复重新计算时，旧孤立行和新 committed 行可以共用一个 step。

实测复用了开发者自身 R1 的无指纹参考反例：权威提交 row_id 为 **[1,3]**，共 2 次评估；导出却有 **3 帧，evaluation_id=[0,1,1]**，同时包含旧 label-6 和新 label-7。

修正：完整轨迹通过权威 commit→row_id→phase 读取，原始孤立行可留作审计记录，但不能自动成为轨迹/配对力样本。验收将恢复后的 `committed_row` 身份与 export 帧逐一核对；本例两次解析力相同，不能因为数值碰巧相同就忽略重复帧。

### A4 [P2] inspect 的步数已修，时间和温度仍来自未完成尾帧

位置：`src/pyraimd2/runtime/inspect.py:134–153`、`:190–196`。

inspect 已按 `STEP_COMPLETED` 计步，却仍从数据库最后一行取温度/能量，从最后 evaluation context 取物理时间。

实测：无任何 complete-step commit 时，inspect 报 **0 个完成步，但时间 0.1 fs、last_step=0**；export 最后可用帧为初态 **0 fs、step=-1**。两者温度也来自不同物理时刻。初始导出本身另有 A1，两个问题应分别验证。

修正：共用完整步视图显示当前轨迹时间/观测量，另设 `last_evaluation` 字段呈现已计算但未完成的状态。允许保留这类诊断信息，但必须明确相位，不能并列成同一个“当前完成状态”。

以上四项可由一个共享的、按任务与 phase 解释 commit 的读取接口解决。应避免继续在 inspect、export、resume 各自补一套互不一致的过滤条件。

## 分项复核结论

### 核心恢复与在线更新：多数原触发点已修，仍有四项同根残留

完整证据见 [核心复核](../../analysis/development_review_040_20260909/core_review.md)，主审已独立复跑其小脚本全部场景。

可以关闭上一轮的具体触发点：pending 检查重复随机数、已入库缓存标签导致额外训练/误报消费丢失、JSON 工件内容修改未检出、训练丢失 cell/PBC/电荷/磁矩、整体平移差分放过错误内部力、候选推理异常和 publisher OSError 不回滚。常规数组落盘也已可用，真实 MACE 新进程加载不再是空缺。下面是修复尚未覆盖的具体路径：

#### C1 [P1] resume 选择了正确行，却仍从旧行取力

位置：`loop/energetic.py:1992–1998`、`store/store.py:225`。

第 1992 行使用 `committed_row`，第 1994 行却调用按 step 取首行的 `driving_label`，随后用这份旧力重建动量。故障注入使重执行参考标签略有不同，以区分两个有效 payload：权威 row=3 的力为 **-0.24136591053875858**，恢复却读取孤立 row=2 的 **-0.24116493975562892**，刚保存的完整步动量被改变 **9.87e-7**（ASE 单位）。分项复核亦以独立进程确认。

这项与 A3 共用根因，但实际影响的是核心原子状态。修正应使位置、力、参考标签和更新重锚全部来自同一个已验证 row；已有有效 checkpoint 边界不应无故被旧数据库状态覆盖。`_replay_label_event` 另外两处旧按步读取点也需一并检查。验收必须让旧行与重新执行的行数值不同，否则会再次漏检。

#### C2 [P1] 数组侧车混淆 shape/dtype，标量也被升维

位置：`runtime/models.py:63–64,120–151`，模型与 checkpoint 的数组写入点。

内容寻址只 hash 字节，加载也仅校验字节，没有核对 shape/dtype。正常保存 `zeros((2,2))` 和 `zeros(4)`，向量会加载成矩阵；相同字节的 `float64([1.0])` 与 `uint64([4607182418800017408])`，后者会加载成 float64 的 1.0。无需损坏文件或崩溃。另 `np.ascontiguousarray` 会使 0-D 状态从 `()` 变成 `(1,)`。

应让数组身份覆盖 dtype/字节序、shape 与内容，并在事件侧车、模型工件、checkpoint 三个入口统一验证、保留标量维度。现有 MACE 那次恢复成功不等于这些字节碰撞路径安全；本轮没有声称已存的 MACE 案例受损。使用 NumPy 即可完成全部针对性回归。

#### C3 [P2] 训练成功任务的日志写入失败仍不回滚

位置：`loop/energetic.py:1422–1428`，而 publication 的 try/rollback 在 `:1467` 才开始。

训练和验证通过后，写 training-success task 时注入 OSError，停止状态仍为候选 k=0.81、n_updates=1，而 generation=0、model_update 事件为 0。原来的 publisher 异常已修，本次缺口在它之前。Runner 会停止，未观察到继续积分。

将接受候选后的日志、state_dict、工件与提交步骤纳入同一回滚域；验收逐一覆盖这些入口，停止时模型、代次、计数与 pending 一致。

#### C4 [P2] 重校准后的未提交 proposal 恢复丢失段状态

位置：`loop/energetic.py:839–848,1124–1125,1164–1173`。

新模型重校准已完成并保存 proposal，但 evaluation 尚未提交时中断，n_label=1 的小例继续后：连续分支 calibration/segment 为 **3/3**，恢复分支为 **2/2**，两边 generation 均为 4、位置相同。已证实的是校准和段历史差异，不能夸大为这个反例的轨迹错误。

将校准完成的 anchor、segment、计数及 deferred 状态作为可恢复变化完整保存/应用，保证恰好一次。覆盖 n_label=1/2 的同窗口即可；暂不支持的窗口应明确拒绝。

### 后端与账本

完整证据见 [后端复核](../../analysis/development_review_040_20260909/backend_review.md)。两条 QE 路径对正常/不完整/未收敛输出的成功判定、目录续号、磁矩和电荷映射、确定性失败不重试、暖启动和原错误清理，大部分旧反例已经真正修好。相对赝势路径和直接 LJ 参数指纹亦通过。

配置驱动的 qe/qe-ase singlepoint、relax、MD，在“首次瞬态失败、随后成功”的路径中均正确计数；新 Al 的 19/19 记录也成立。以下残留不应被用来否定这些通过项，但表明通用接口与失败路径尚未全部一致。

#### B1 [P1] ASE 包装计算器仍有物理身份碰撞

位置：`engines/ase_engine.py:89–100`。对应后端复核 F1。

修复对直接 LJ 有效，但 `SumCalculator([LennardJones(epsilon=1)])` 与 epsilon=2 的 `parameters={}`，当前指纹仍相同，实际同构型能量相差一倍。JSON 可序列化不等于包含了全部物理设置。

对未知完整性或包装计算器，返回未知身份/要求显式 identity 即可；若选择支持组合身份，则纳入子计算器和权重。无需为所有 ASE 类都实现一个新适配器。验收要求该例不能继续得到相同的非空可信指纹。

#### B2 [P1] Python API 中 Runner 有日志、engine 没有日志仍漏记内部重试

位置：`runtime/events.py:84`、`engines/qe_engine.py:765`、`loop/energetic.py:988`。对应后端 F2，主审直接复现。

直接构造 QeEngine 不传 optional event_log，再向 EnergeticRunner 传日志，程序接受此组合。包装层仅凭 compute 接收 `request_id` 就认定后端会上报 attempt，实际 engine 无接收器。结果仍是实际启动 **2 次**，账本 **logical=1、actual=1、failed=0**。

必须显式连接接收器、通过调用参数传递 attempt sink，或消费完整后端执行记录；无法支持的组合在启动前拒绝。不能回退成外层一条 attempt 来掩盖内部重试。验收应变成 1/2/1，并保留已正确的配置工作流和 Al 19/19。

#### B3 [P1/P2] 真实启动、失败终结与耗时仍需统一（后端 F3–F7）

这些属于 R6 同一套账本接口的残留，不拆成新的功能计划；具体触发、行号和数值在分项报告中：

- **P1，ASE 隐式额外执行：** 缺 stress 时，先取 energy/forces、再 get_stress 会使 ASE 再次执行；max_retries=0 仍实际启动 2 次，只记 1 条 attempt。标签最终拒绝是正确的，真实执行数仍错。应在一次明确执行后读取整份结果，并在实际执行入口记录启动。
- **P2，零启动误计：** 可执行文件不存在时，ASE 包装层会记一次 attempt；手写 QE 没有误发 attempt，但汇总以“有无任意 attempt”判断 legacy，又把全新零启动日志的失败任务计为一次 SCF。新日志必须按显式协议判断，不依赖是否恰好曾启动成功。
- **P2，后处理失败漏记：** 进程已成功、写 density manifest 失败，两路径实际启动 1 次，却无 attempt 事件，有的内存记录仍为 running。进程一旦启动，后处理异常也要终结其记录；解析成功、程序成功与后处理失败可以分开描述。
- **P2，首次失败无父请求：** ordinary relax/MD 首次求值未收敛时，两路径均 actual=1、logical=0，attempt 的 request_id 无父 task。每次逻辑调用在统一 try/finally 内完成记录，不因失败换 task ID。
- **P2，耗时口径：** 密度拷贝发生在 process attempt 计时开始前，却被汇总当作已包含而排除；静止 MD 的缓存命中又沿用旧 SCF 的 wall_time，实际只执行一次但汇总可为三倍。使用本次缓存访问耗时，并按真实时间段决定 I/O 是否另计。

最小验收是：实际进程进入次数等于 physical attempt 数；零启动为 0；每次逻辑调用有正确父 ID；所有已启动 attempt 在失败后有终态；缓存与复制耗时按实际区间汇总。仅需假程序和解析输入，不要求再次动用真实材料算力。

## 交回开发者的收尾建议

下一轮仅做已经定位的正确性补丁。每项回复：原因、修复提交、原反例修复后的可核对输出、对应新增回归以及必要的兼容说明。不要用测试总数代替每一条问题的验收。
